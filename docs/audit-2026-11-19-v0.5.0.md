## 3. 主要改动

### 3.1 迁移与升级

- `server/internal/db.Plan`：只读迁移计划（applied/pending/latest/schema_ready）。
- `server/cmd/migrate`：`-status` / `-apply` / `-json` / `-timeout`；Docker 镜像同时包含 `nover-api`、`nover-maintenance`、`nover-migrate`。
- Compose 新增 `ops` profile 的 `migrate` 服务；web/console 增加 Nginx 健康检查与 `depends_on: api healthy`。
- `/api/v1/meta` 增加 `schema_version`；`GET /api/v1/cp-7f3c/system/status`（`settings.read`）汇总应用/数据库/迁移/存储状态。
- 控制台部署设置新增系统状态卡（版本、commit、环境、运行时长、DB 延迟、迁移 applied/pending/latest、存储可写；pending>0 醒目告警），用户端页脚与控制台顶栏显示版本。
- `scripts/ops/upgrade.ps1`：预检、镜像记录与 `:previous` 标签、自动备份、构建启动、就绪等待、系统状态摘要、`-Rollback`；`-DryRun` 只打印计划。
- [docs/upgrade.md](upgrade.md)：升级前检查、一键升级、回滚、手工迁移、升级后验证与故障处理。

### 3.2 测试体验

- 新增 `//go:build integration` 集成测试：真实 PostgreSQL 上执行迁移、登录、商品/版本/文件上传、兑换、交付、下载、退款、邀请、MFA 两步登录与系统状态；测试创建合成数据并在结束时清理。
- CI 新增独立 PostgreSQL service 的 integration job。
- `scripts/verify.ps1` 增加 `-Integration`（需要 `TEST_DATABASE_URL`）与 `-ReportPath`（JSON 报告），默认行为不变。
- 本次验证报告：9 项通过、0 失败、0 跳过，耗时记录完整。

## 4. 剩余风险与边界

1. **升级/回滚未真实执行**：脚本只做了 dry-run 与失败路径 shim 验证；首次生产升级前必须在隔离环境演练完整升级 + 回滚。
2. **备份恢复未演练**：`backup.ps1` / `restore.ps1` 仍只有 dry-run/校验路径证据；建议季度演练。
3. **回滚边界**：`upgrade.ps1 -Rollback` 只回退镜像，不自动回退数据库迁移；破坏性迁移需恢复备份。
4. **无 v0.5 数据库结构变更**：迁移仍为 `0001`–`0004`，因此升级路径本身较简单；未来迁移需沿用 `nover-migrate` 状态检查。
5. **控制台 UI 验证**：系统状态卡与版本显示通过构建、产物字符串和静态审查验证，尚未做真实浏览器/键盘回归。
6. **CI 首跑**：新增 integration job 与 smoke 时长需在 GitHub Actions 首次运行确认。
7. **版本来源**：前端版本来自 API 构建注入；未设置 `APP_VERSION` 时显示 `dev`，属于预期行为。
8. **会话累积**：本地 sessions 持续增长，维护命令可清理；生产应配置 cron。

## 5. 建议下一步

1. 在隔离环境执行一次完整升级 → 验证 → 回滚 → 恢复演练，并把结果写入运维记录。
2. GitHub CI 首跑（integration + smoke），观察总时长与资源。
3. 控制台系统状态卡/版本展示做浏览器与可访问性回归。
4. 为 `verify.ps1` 报告增加 HTML/摘要输出（可选），并将 integration 测试加入 PR 必跑。
5. 后续大版本：RLS/跨租户负向矩阵、S3/扫描、告警/追踪、MFA 运维闭环。
